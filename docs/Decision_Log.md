# Decision Log

Stable, load-bearing decisions only. One-line rationale per entry. If a decision is reversed, strike it through and add a new entry rather than deleting history.

## Format

`YYYY-MM-DD — Decision. Rationale. Impact.`

Date is approximate (when easy from git or memory). When unknown, leave blank rather than invent.

## Decisions

- **2026-06 — Base mainnet is a read-only demo profile.** Rationale: we want a public-facing surface for the exchange UI without exposing write paths until on-chain hardening and audit. Impact: web mainnet build must surface "Read-only mode" affordances; API must keep watchers off; no Smart Intent submit allowed.
- **2026-06 — Sepolia is the full interactive QA / demo environment.** Rationale: clear separation of where real EIP-712 sign + on-chain settlement is exercised end-to-end. Impact: all destructive-path QA happens on Sepolia.
- **Permanent — Backend never signs EIP-712 and never custodies private keys.** Rationale: Web3 safety boundary; non-negotiable. Impact: all signing stays in the wallet; backend only verifies signatures and forwards built tx data.
- **Permanent — Normal Market and Limit behavior is regression-protected.** Rationale: these are the load-bearing flows that any user touches first. Impact: SEA work and UI polish must not alter Market/Limit semantics; changes here require explicit task.
- **Permanent — CL uses pre-signed passive 0x limit orders.** Rationale: matches the existing maker pipeline; no special-case settlement. Impact: CL fire path only writes the underlying Order; existing matching/settlement is reused.
- **Permanent — CMR requires user confirmation; no auto-execution.** Rationale: avoid surprising on-chain spend without an explicit click. Impact: CMR READY only arms the row; the user must `Execute now` to sign the wallet-lock.
- **Permanent — CMR READY requires the full requested size fillable at or better than the trigger.** Rationale: "execute the full requested size or do not start" is the intent the user purchased. Impact: `cmr-prepare.service.ts` enforces `remainingBase === 0n` independent of TIF.
- **Permanent — CMR executable quote is built after wallet-lock.** Rationale: book may have drifted; we rebuild against the latest LOB inside the locked window. Impact: `/match/quote` is the second-stage gate; `fok_insufficient_liquidity` is the recoverable failure mode.
- **2026-06 — New CMR intents use fixed `tif="FOK"` and the UI selector is hidden.** Rationale: IOC/FOK was dead UI; semantics are enforced by READY + FE guard; FOK adds one server-side defense-in-depth. Impact: existing CMR rows with `tif="IOC"` still work; new rows persist as FOK.
- **2026-06 — PLACED Smart Intents are UI-history, not live.** Rationale: once PLACED, the underlying normal Order takes over and lives in OrdersPanel. Impact: PLACED rows hide behind `Show history`; users cancel via Orders panel; no Smart Intent state-machine change.
- **2026-06 — Cancel/fill of the linked normal Order does NOT transition the Smart Intent out of PLACED.** Rationale: avoids a complex cross-domain sync; v1 keeps the two panels independent. Impact: PLACED Smart Intents remain PLACED until user cancels them or they expire; documented limitation, not a bug.
- **Permanent — Mainnet API must keep `DEV_ONCHAIN_WATCHER=0`.** Rationale: read-only profile must not run write-path reconciliation. Impact: FillWatcher / CancelWatcher disabled on mainnet; only Sepolia or local exercises them.
- **Permanent — `clear-sea-intents-dev` is local/dev only and deletes only `IntentEvent` + `Intent`.** Rationale: surgical reset for QA; never touches Order, Trade, OrderEvent, BookSnapshot, Market, Token, or CancelPairFloor. Impact: safe to re-run for SEA QA cycles; multi-guard refusal (CONFIRM env, READ_ONLY, PROFILE=mainnet, non-local DB host).
- **Permanent — Smart Execution Assistant (AI/NL) will be a layer on top of the deterministic engine.** Rationale: critical execution logic stays deterministic and auditable; LLM is only for parsing/explanation/UX. Impact: future AI work must not move execution control into LLM logic.
- **2026-06-06 — UI uses `displayAmount()` (display-only) for all rendered token amounts; internal bigint math is unchanged.** Rationale: `ethers.formatUnits()` can produce float artifacts (e.g. `100000.00000000001`) in displayed strings. `displayAmount()` in `format.ts` applies `Intl.NumberFormat` with bounded precision for rendering only; the raw bigint value is never altered. Impact: TradePanel allowance/spend messages and BalancesPanel balances render cleanly; no change to approval amounts, validation, wallet payloads, or API contracts.
- **2026-06-06 — Visible "STE"/"SkyTrade" product strings removed from UI.** Rationale: pre-deploy branding cleanup; internal identifiers, env vars, filenames, and API routes are unchanged. Impact: browser title, footer text, and ConditionalTab help copy use neutral wording ("Exchange", "Hybrid Exchange", "the engine").
- **2026-06-07 — Visual UI polish pass accepted; page background is `bg-[#27374b]`.** Rationale: a slightly lighter/richer blue-gray improves card elevation over the prior `slate-800`; card border/shadow, header divider, and harmonized address/wallet/selector pill surfaces were accepted in visual QA. Impact: visual/class-only; no change to layout behavior, Market/Limit/SEA logic, or read-only handling.
- **2026-06-07 — "Cancel orders" is advanced/secondary UI, collapsed by default.** Rationale: destructive pair-cancel + raw-orderHash controls should not be primary/always-open. Impact: rendered inside a native `<details>` (title/description visible when collapsed); the exact controls and read-only guards are unchanged on expand.
- **2026-06-07 — `displayAmount()` renders sub-precision positive values as `<0.000001`, not `0`.** Rationale: showing `0` for a tiny non-zero balance is misleading in a financial UI. Impact: display-only floor string; underlying bigint values and approval/validation paths unchanged.

- **2026-06-09 — Local Sepolia API sets `PROFILE=sepolia` explicitly.** Rationale: `main.ts`'s unconditional `import 'dotenv/config'` loads `apps/api/.env` (mainnet) at boot; without an explicit profile in `.env.sepolia`, `PROFILE=mainnet` leaked in and hard-disabled the SEA monitor. Impact: the launcher now runs as `sepolia`; IntentMonitor starts (`cmr=on`) and CMRs reach READY. `.env.sepolia.example` carries the same line. `.env.sepolia` stays gitignored (secrets).
- **2026-06-09 — CMR wallet-lock uses the FE-supplied, server-proposed, owner-signed `walletLockUntilAt` as the source of truth.** Rationale: the old design recomputed `now + lockSec` at POST time and required ≤5s equality, so any human signing delay failed with `wallet_lock_until_mismatch`, and it verified the signature against the recomputed value rather than the signed one. Impact: `lockWallet` bounds-checks the supplied value (finite, future, ≤ expiresAt, ≤ now + lockSec + grace) and verifies the signature against it; no silent clamp.
- **2026-06-09 — Wallet-lock is idempotent for the same lock and immutable for a different live one.** Rationale: a live lock must not be replaceable. Impact: a re-POST with the same `walletLockUntilAt` returns the same executionToken without re-verifying; a different value while a live lock exists is rejected (`wallet_lock_until_mismatch`) with no re-lock/extend/new token.
- **2026-06-09 — CMR v1 READY requires a single-fill executable quote.** Rationale: CMR v1 executes one market-fill tx; an aggregate fill spanning multiple maker orders is not executable (the FE refuses split/multi-tx). Impact: `CmrPrepareService` and `freshQuote` require `fills.length === 1` (plus the existing `remainingBase===0` + notional); otherwise the intent stays ACTIVE with PROGRESS `requires_single_fill`.
- **2026-06-09 — CMR stale-window mitigation: FE 60s pre-send buffer + backend 45s markExecuting grace.** Rationale: a wallet-lock can expire while the user reviews/signs, orphaning an on-chain fill. Impact: the FE refuses to open the wallet when <60s lock remains; the backend marker accepts a fill confirmed up to 45s past the lock (token-bound, status READY, unchanged `preparedQuoteAt`), and the monitor blocks READY re-arm during that grace.
- **2026-06-09 — Known v1 limitation: a wallet confirmation many minutes beyond lock + 45s grace may not reconcile.** Rationale: the FE cannot act while the wallet modal is open, and the FillWatcher links only EXECUTING rows. Impact: in that edge the on-chain fill is correct but the Smart Intent may show ACTIVE/EXPIRED; the user is told to verify wallet/chain activity. Deferred (no new intent state in v1).

- **2026-06-15 — SEA AI Assist (Phase 1) is an LLM-extractor-only layer; deterministic code is authoritative.** Rationale: keep all execution-critical logic deterministic and auditable; the LLM only turns natural language into a restricted draft. Impact: new stateless `POST /sea/ai/parse` (gated by `SEA_AI_ENABLED`, Anthropic provider behind an interface, `ANTHROPIC_API_KEY` server-side only) returns an in-band `validDraft | needsClarification | unsupportedIntent | aiUnavailable`. The LLM never sets reference/triggerType/ticks/tif/enforcement/executionAuthority (all derived in code; MID never produced) and never emits user-facing prose (every summary/question/note/reason is code-generated); a vague/missing price → `needsClarification`, non-price strategies (RSI/MA/news/forecast/portfolio) → `unsupportedIntent`. No auto-execution, no session keys/delegation, no DB conversation store. The existing signed create flow + `validateAtCreate` remain the only path to an intent. `rawText`/`parserMeta` are optional, non-signing provenance attached on create **only when the form still matches the applied AI draft** (subMode + market + side + size + trigger + CL limit), so a manual edit or a submode/market switch detaches stale metadata.

- **2026-06-20 — Phase RPC-1: watcher RPC/quota resilience without changing the polling/cursor model.** Rationale: Alchemy free-tier 429/quota exhaustion was hammering the watchers every 2s and breaking order placement, with no backoff. Impact: additive, env-gated changes only — no `getLogs`/WebSocket rewrite, no shared provider pool, no settlement/cancel/matching semantic change. New `apps/api/src/onchain/rpc-transient.util.ts` (`isTransientRpcError`, `Backoff`, `resolveWatcherEnabled`).
- **2026-06-20 — Watcher enable gates split with backward compatibility.** Rationale: independent control to run only one watcher (lower RPC) for QA. Impact: `DEV_FILL_WATCHER` / `DEV_CANCEL_WATCHER` — `"1"` enables, `"0"` disables, **unset inherits the legacy `DEV_ONCHAIN_WATCHER`**, so existing configs behave identically. FillWatcher also gains `FILL_WATCHER_MAX_BLOCKS_PER_TICK` (mirrors CancelWatcher) and both gain `FILL/CANCEL_WATCHER_INTERVAL_MS`.
- **2026-06-20 — Transient-only backoff + cooldown on 429/quota; cursor never advances while degraded.** Rationale: a throttled provider must not be re-hit every tick, and events during the pause must not be skipped. Impact: on a transient RPC error (429/5xx/rate-limit/quota/capacity/timeout/network) the watcher logs once, sets an exponential cooldown (`WATCHER_RPC_BACKOFF_BASE_MS`/`MAX_MS`, 15s→120s), returns without advancing the cursor, and retries the same block after cooldown; the first clean tick resets the backoff. Non-transient errors (ABI/decode, bad address/config, revert) are classified non-transient and surface exactly as before.
- **2026-06-20 — Watcher boot is self-healing on transient RPC failure.** Rationale: a boot-time 429 used to leave the watcher permanently dead until a process restart. Impact: a transient boot error emits a `boot_degraded` warning, starts the timer in cooldown, and defers cursor initialization to the first successful tick — the persisted cursor is never reset while RPC is down. A non-transient boot error keeps the prior `boot_failed` + no-timer behavior so config errors stay loud.
- **2026-06-20 — Order-placement maker balance guard degrades to warn-skip on transient RPC error.** Rationale: a 429 during the `balanceOf` guard was 500-ing placement and SEA fire; the guard is a soft pre-check and on-chain settlement is authoritative. Impact: a transient RPC error in `orders-placement.service.ts` now warns and skips the guard (consistent with the existing missing-RPC skip) instead of failing placement; the `maker_insufficient_free_balance` rejection still fires when the balance is genuinely read and insufficient; non-transient errors (ABI/address/config) are rethrown.

- **2026-07-07 — Delegated CMR (optional second execution mode) validated in a Phase 0 spike and scaffolded in Phase 1; provider = Biconomy Smart Sessions + Nexus behind a thin interface.** Rationale: activate the reserved `DELEGATED_FUTURE` authority as a separate, opt-in layer without weakening manual CMR — the user authorizes once and a backend-held, policy-scoped **session key** (never the user's key) executes the 0x fill later. A throwaway Sepolia spike (outside the repo) proved the safety model on-chain: Nexus-SA mock abuse matrix 10/10 (target/selector/usage=1/expiry/revoke/spend-cap all enforced), the **EIP-7702** path (funds stay in the user's EOA; the EOA is the 0x taker), and a **real 0x `fillLimitOrder`** filled through a session (usage=1 blocked the replay). Impact: **EIP-7702 delegated EOA is the preferred account model; deployed Nexus SA is the universal fallback; manual CMR is the fallback for unsupported wallets.** v1 gas is account-funded (no paymaster/sponsorship). On-chain notional bound for fills is a UniversalActionPolicy calldata param-rule on `takerTokenFillAmount`; the session key signs the userOp hash with raw ECDSA (not EIP-191); the SA is pre-deployed via a direct factory call (ERC-7562). STE-side fresh-quote validation remains the authoritative economic guard; the session policy is a coarse backstop.
- **2026-07-07 — Delegated CMR Phase 1 is a fully-disabled, multi-profile, additive scaffold only.** Rationale: land types/config/DB/provider-interface/guards without any live execution or SDK wiring. Impact: default-OFF everywhere (`SEA_DELEGATED_ENABLED=0`, `SEA_DELEGATED_EXEC_ENABLED=0`, `SEA_DELEGATED_PROVIDER=mock`); config is **profile-keyed** (`ethereum-sepolia` writable / `base-mainnet` hard-disabled-read-only, unknown → base-mainnet as the safe default); the executor worker never boots in Phase 1; the Biconomy SDK is **not** added to the repo (mock/noop provider only); new Prisma models (`DelegationGrant`, `DelegatedExecutionAttempt`) use a plain `intentId` string with **no relation to `Intent`**, so the Intent model and manual-CMR/wallet-lock logic are byte-for-byte unchanged; every write/exec path passes `delegationWriteGate` (belt-and-braces re-checks `READ_ONLY` + `PROFILE=mainnet`). - **2026-07-07 — Delegated CMR Phase 2: real Biconomy provider + live executor, still default-OFF and additive.** Rationale: fill the Phase 1 provider seam with the spike-proven Biconomy Smart Sessions + Nexus flow without touching manual CMR. Impact: added `@biconomy/abstractjs@1.2.4` + `viem@2.54.3` to `apps/api`, **dynamic-imported only inside the Biconomy adapter** (never loaded when `SEA_DELEGATED_PROVIDER=mock` or disabled → never in CI). `grant` became a **non-custodial prepare/finalize split** (backend builds the enable digest; the USER signs it in their wallet; finalize persists the ACTIVE grant). The backend holds only the scoped **session signer** (`DELEGATION_SESSION_SIGNER_PK`, server-only, never logged/exposed, loaded only when enabled on a writable profile; rotation invalidates outstanding grants). The **executor self-confirms from the userOp receipt** by verifying the 0x `LimitOrderFilled` event (orderHash + taker + fill amount) — never trusting tx status alone, never faking success — because the existing FillWatcher only decodes top-level `fillLimitOrder` calldata and cannot see a userOp-wrapped fill (so **FillWatcher is untouched**). The delegated lifecycle (`READY→EXECUTING→EXECUTED/FAILED`) is written by a **new dedicated race-safe repo** (compound-where `updateMany`), never editing `IntentRepository`/`intent.service`; a pre-submit failure **releases back to READY** so manual CMR fallback survives. Policy = single target (0x EP) + selector (fillLimitOrder) + usageLimit=1 + validUntil + UniversalAction bound on `takerTokenFillAmount` + ERC-20 spend cap over `takerAmount + fee`; STE fresh-quote validation stays the authoritative economic guard. Everything default-OFF (`SEA_DELEGATED_ENABLED=0`, `SEA_DELEGATED_EXEC_ENABLED=0`), base-mainnet hard-disabled, no paymaster (account-funded gas). Frontend delegated UX deferred to Phase 3.

- **2026-07-12 — Delegated CMR Phase 2 adapter: three fixes to make the real Sepolia execute pass (proven by live E2E, fill tx `0x03968c1e…`).** Rationale: the non-custodial `getEnableSessionDetails` execute path reverted `AA23` where the Phase 0 spike's custodial `grantPermissionPersonalSign` path succeeded; a side-by-side structural comparison + inner-revert decode isolated three divergences, each reconciled to the spike-proven behavior. Impact (all in the untracked `sea/delegated/biconomy-delegation.provider.ts`, no sensitive/frontend file touched): (1) **session validator** must be the deployed OwnableValidator `0x000000000013fdB5234E4E3162a810F54d9f7E98` (module-sdk `GLOBAL_CONSTANTS.OWNABLE_VALIDATOR_ADDRESS`, what the SDK's own grant helper uses) — **not** the stale top-level `OWNABLE_VALIDATOR_ADDRESS` re-export (`0x2483…`) that abstractjs/module-sdk also expose; pinned as a literal because module-sdk isn't a direct apps/api dep (canonical CREATE2 address, chain-independent). (2) **`ignoreSecurityAttestations: true`** must be passed to `getEnableSessionDetails` (its default is `false`; the grant helper hardcodes `true`) — with `false` the SmartSession enforces ERC-7484 Registry attestations on the Sepolia-unattested validator/policies and the enable reverts. (3) **Do not attach `getSpendingLimitsPolicy`** to the `fillLimitOrder` action — it parses ERC-20 approve/transfer calldata, can't decode a 0x fill, and rejects with `PolicyViolation`; the **UniversalActionPolicy param-rule** (`takerTokenFillAmount ≤ maxTakerFillAmountQ`) is the on-chain notional bound (the spike's proven "C_paramRule"), with STE fresh-quote validation remaining the authoritative economic guard. Non-custodial split, receipt self-confirm, usageLimit=1 replay-block, default-OFF, base-mainnet inert, and manual-CMR/CL boundaries are all unchanged.

- **2026-07-12 — Delegated CMR fee exposure is bounded STE-side + receipt-verified, NOT by an on-chain fee param-rule (accepted model).** Rationale: after removing the SpendingLimitsPolicy (can't parse a 0x `fillLimitOrder` call), the question was whether to restore an on-chain fee bound via a UniversalActionPolicy param-rule. It is **not reliable**: the only fee-related calldata word is `order.takerTokenFeeAmount` (word 4) = the maker order's fee for filling the _whole_ order, while CMR single-fill can _partially_ fill a larger maker order (actual fee = `takerTokenFeeAmount × fill / takerAmount`). There is no calldata word for the actual proportional fee and param-rules can't express a ratio, so a word-4 cap set to the intent's fee buffer would wrongly reject legitimate partial fills of larger orders. Impact — accepted security model: (1) **on-chain** the session caps `takerTokenFillAmount` (word 16 ≤ `maxTakerFillAmountQ`) — reliable, tied to the fixed intent size — plus target+selector+usage=1+validUntil; (2) **STE-side** the fresh-quote validator caps the actual `takerAmount + takerTokenFeeAmount` at execute time (order known) — authoritative; (3) **receipt verification** now also confirms the actual fee: `verifyFill` requires `LimitOrderFilled.takerTokenFeeFilledAmount ≤ expected.takerFeeAmount` (the STE-computed proportional fee), added to the existing orderHash+taker+takerToken+fillAmount check, so an over-fee fill is not marked confirmed; (4) no calldata is stored/logged before READY validation (built read-only in the fresh-fill pass). Removing the SpendingLimitsPolicy introduced **no broader permission** — the session is strictly narrower (one target, one selector, usage=1, expiry, fill-size cap). All additive, inside the untracked `sea/delegated/**`; no sensitive/frontend file touched.

- **2026-07-12 — Delegated CMR Phase 3 uses the Nexus Smart Account model, NOT EIP-7702, for the browser path (EIP-7702 deferred).** Rationale: the Phase 3.0 manual test showed MetaMask/injected cannot dApp-drive an EIP-7702 authorization to the Nexus implementation (`signAuthorization` throws `AccountTypeNotSupportedError` for json-rpc accounts, there is no `eth_signAuthorization` RPC, and `eth_getCode` stayed `0x`), whereas Phase 3b.0 proved (a) the real Phase 2 backend fills with a Nexus SA as the 0x taker (`execute(accountModel='NEXUS_SA')`, fill `0xc03afa15…`, taker=SA, replay usage=1 blocked, escape-hatch withdraw) and (b) a **real MetaMask** wallet can own a Nexus SA and sign its userOps (approve `0x1dde68b2…` bounded allowance 1,000,000; withdraw `0x15ca8010…`). Impact: Phase 3b builds the Nexus-SA delegated UX where **delegated funds live in the smart account** (explicit deploy → fund → bounded approve → install SmartSessions → grant; mandatory withdraw/escape hatch); EIP-7702 stays deferred as a later coverage improvement. Manual CMR remains the universal fallback (untouched); everything default-OFF, base-mainnet read-only, account-funded gas (no paymaster), no backend user-key custody. **Only MetaMask owner-userOp signing is proven — Web3Auth v10 owner signing is unproven and must be capability-gated in the frontend (no Web3Auth delegated support claimed).**
